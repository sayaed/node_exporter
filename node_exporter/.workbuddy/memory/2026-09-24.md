## node_exporter 自定义采集 broken pipe 排查（只读分析，未改代码）

**现象**：scrape_interval=10s，日志反复报

**结论**：报错来自 client_golang 的 promhttp（v1.23.2 第 231 行；当前 go.mod 已是 v1.24.1，对应第 358 行 → 说明线上二进制是旧版本编的）。

3. 5 个采集器各自 glob `/proc/[0-9]*` 并重复读 pid 文件，无共享快照；已写好的 `parsePasswdFile()`（5min TTL 缓存，user_utils.go:219）只在 diskinfo 里用到，基本是死代码。

## 能否全部改用 /proc 采集（承接上一节）

- **可直接替换**：`usershm` 的 `ipcs -m` → `/proc/sysvipc/shm`（逐行空白分隔，含 shmid/perms/size(字节)/cpid/lpid/nattch/uid/gid/...；给的是 **uid 数字**，正好接 uid→用户名 map，比现在 `user_shm.go:187-195` 按列数猜字段可靠得多）；`ipcs -m -l` → `/proc/sys/kernel/shmmax`(字节) + `shmall`(**单位是页，需 ×page size**) + `shmmni`(段数上限)；SHMMIN 无 /proc 对应（内核硬编码 1）。
- **不能替换**：`user_diskinfo` 的 `du -sb`。`/proc` 里没有任何「目录占用」信息。三条出路：① home 若是独立挂载点 → `/proc/self/mountinfo` 定位挂载点 + `statfs()` → O(1)；② 文件系统支持 XFS/ext4 project quota → `quotactl(Q_XGETQUOTA)` → O(1)；③ 都不满足 → 后台 goroutine 采样 + RWMutex 缓存，`Update()` 只读缓存。
- **procfs v0.22.0 不含 sysvipc 解析**（已确认查过），需本地按行解析，或按 AGENTS.md 建议给上游提 PR 加 `procfs` 支持。
- **顺手可省的 I/O**：① 取进程 uid 用 `stat("/proc/<pid>")` 的 st_uid，不必读 `/proc/<pid>/status`；② 线程数取 `/proc/<pid>/stat` 第 20 列 `num_threads`，不必 `ReadDir(/proc/<pid>/task)`；③ `ExtendedProcessInfo.CgroupData`（user_utils.go:158/209）全库无引用，纯浪费 I/O；④ `user_cpu.go:133-148` 的 per-pid goroutine+5s ctx 包装可删（本地文件读无法被 ctx 取消）。
- **发现的正确性 bug**：`user_cpu.go:127` 用 `strings.Fields` 直接切 `/proc/<pid>/stat`，comm 含空格时（如 "Web Content"）所有列右移，utime/stime 静默取错；应像 `user_io.go:236` 那样以最后一个 `)` 为界切分。

### userdiskinfo 缓存语义（用户问询后核实）

- **interval 不是周期**：sleep 在每轮 pass 之后，实际发布间隔 = interval + 本轮耗时（5m/5m 下最坏 10min）。
- **timeout 不是数据有效期/丢弃时间**：它是单轮 pass 的整体 deadline（`context.WithTimeout`）。超时的后果只有一个——本轮未轮到的目录**沿用上一轮值**，数据不丢。
- **轮内不更新缓存**：新测到的数据先进本轮局部 `sizes` map，只有 `measureUserdiskSizes` 返回后整个快照才换指针发布。所以抓取永远看不到"半轮混合"，但也看不到轮内最新值。
- **整轮粒度混合**：发布时会把本轮没测到的路径（du 报错/超时 → 未写入 `sizes`）用上一轮值填满，`cache.taken` 同步刷新为轮末时间。

### 实施三：修掉上面的陈旧掩盖缺口（已改代码，**未提交**）

问题本质：`taken` 只有整轮粒度 → 单个目录可以无限期沿用旧值而 `cache_age_seconds` 每轮归零，指标静默冻结。

改法（**只在这一个 collector 内，不加任何 flag**）：

  - `userdiskDirStat{size int64, taken time.Time}` —— **时间戳下沉到每目录**。
  - `(userdiskDirStat) stale(now, staleAfter) bool` —— 唯一的陈旧判定，`Update()` 与 `staleUserdiskPaths()` 都走它，避免两处逻辑漂移。

  - `userdiskCache.sizes` 由 `map[string]int64` → `map[string]userdiskDirStat`；worker 写入时带 `time.Now()`。
  - merge 旧值时**连原 `taken` 一起继承**（`sizes[path] = stat`），这是整个修复的关键一行。
  - `Update()` 里 `stat.stale(scrapeTime, userdiskStaleAfter)` 为真则**不发这条序列**（而非发旧值）；`scrapeTime` 在循环外取一次，全轮同一时间基准。

### 环境关键参数（用户提供，用于容量决策）

- 家目录数量：**几十 ~ 100**

### 实施四：并发上限 8 → 32（已改代码，**未提交**）

用户明确要「按 CPU 核数动态调整」，最终确认 `maxUserdiskWorkers = 32`（公式一字未动，仍为 `min(max(runtime.NumCPU(), 1), maxUserdiskWorkers, len(paths))`）。

**关键澄清（我一开始答错了方向）**：这个式子**本来就是按核数动态的**，问题只出在上限数值。因为用户核数起点恰好 = 旧上限 8，导致 8~128 核区间**全部饱和成 8**，看起来像固定值。把上限抬到 32 后，8~32 核区间真正随核数变化，32 核以上封顶。实测公式输出（已用临时程序验证）：

| 核数 | 1 | 2 | 4 | 8 | 16 | 24 | 32 | 48 | 64 | 128 |
|---|---|---|---|---|---|---|---|---|---|---|
| 并发（100 目录） | 1 | 2 | 4 | 8 | 16 | 24 | 32 | 32 | 32 | 32 |

讨论中确立的结论（值得复用）：
- `NumCPU * k` 这种**乘数**写法方向是反的 —— 4 核机器会得到 16 并发，比 8 核机器还猛；想要"小机器保守"应该用 `max(NumCPU, 下界)` 这种**下界保护**写法。
- **任何带上限的公式必然在上限处饱和**。要让核数项在 8~128 核全区间生效，上限得 > 512，等于放弃保护，荒谬。所以"完全跟随核数"对 I/O bound 任务是不可取的。
- `du` 是 **I/O bound**（开销在 `getdents()` + `lstat()`），核数只是弱信号：它约束的是记账开销，不是文件系统能承受多少并发。真正物理正确的自变量是**实测反馈**（跑完一轮看耗时自适应），但 100 目录规模下属过度设计，未采用。
- 32 以上封顶是刻意的：防止 128 核机器把 128 个 du 压到共享磁盘上，而 100 个目录根本受益不到。

超时分支 `close(statChan)` 时 worker 仍在跑（`wg.Wait()` 未返回），其 `statChan <- stat` 会 **send on closed channel → panic → 整个 node_exporter 进程崩溃**（goroutine 内 panic 无人 recover）。触发条件：`len(coreLabels) >= 2` 且处理超过 30 秒（慢存储/NFS 上的大量 core 文件）。

### P0-2 无消费者的 I/O

- `user_proc_snapshot.go:128` 仍读 `/proc/<pid>/io`，但 `IOData` **已无任何消费者**（`user_io.go` 已删）。且非 root 读他人进程必然 EACCES。**占快照每 pid I/O 的 1/3，白读。**
- `ExtendedProcessInfo.StatData` 同样已无消费者（`user_cpu.go` 已删）。
- `GetAllProcesses()`（不带 Extended）**已无任何调用者**，纯死代码。
- `/proc/<pid>/cgroup` 之前已删，本次确认仍无消费者。

### P1 快照缓存了过大的数据

`userProcInfo.Status []byte` 缓存完整 `/proc/<pid>/status`（约 1.5KB/进程），而唯一消费者 `user_meminfo` 只要 `VmRSS` 一个数字。1000 进程 → 常驻 ~1.5MB + 每 2 秒重建产生 1.5MB 垃圾。应下沉解析：快照直接存 `RSSKB uint64`（8B/进程），内存降约 200 倍。同理 `Stat []byte` 只需保留已解析的 `Threads`。

### P1 user_corefile.go 重复 stat

每个 core 文件被 **stat 2 次**：`parseCoreLabels` 里 `os.Stat` 拿 uid（丢弃 ModTime），`processCoreStat` 又 `os.Stat` 拿 ModTime。应改为 `os.ReadDir(prefix)` + `entry.Type().IsRegular()`（来自 dirent，免费）+ 一次 `entry.Info()`，从 2 次降到 1 次。另外整个 goroutine 池 + 2 个 channel + `wg.Wait` + 30s timer 只为几百次 `os.Stat` 服务，顺序执行即可且能顺带消灭 P0-1 的 panic。`runtime.GOOS != "linux"` 判断是死代码（文件已带 linux 构建标签）。

### P2 其他

- `node_user_core_file_info` 带 `filepath` 标签 → 高基数，随 core 文件累积线性增长序列数。
- `parseProcEnv` / `parseMemEnv` / `parseCoreEnv` 三个别名函数都指向 `parseUserEnv`，可收成一个。
- `filepath.Glob("/proc/[0-9]*")`（快照）有排序开销，`os.ReadDir` + 数字前缀过滤更直接。
- `user_meminfo.go:134` `bufio.NewScanner(strings.NewReader(string(statusData)))` 复制整个 status，若下沉解析则消失。
- README 采集器表仍未收录这 5 个采集器。

### 关于 `/proc` 文件读取分配（源码级结论）

Go 1.25 `os.readFileContents` 有专门的 `zeroSize` 分支，源码注释直接点名 procfs：
```
const minBuf = 512
// ... files in Linux's /proc claim size 0 but then do not work right if read in
// small pieces ...
if size < minBuf { size = minBuf }
...
if capRemain == 0 || (zeroSize && capRemain < minBuf) { data = slices.Grow(data, minBuf) }
```
所以 `os.ReadFile` 一个 1.5 KB 的 status 文件 = 512 → Grow 1024 → Grow 2048，**3 次分配、约 3.5 KB 垃圾**，乘 3 个文件乘 N 进程。换成每 worker 一个预分配 4096 的复用缓冲后为 0。
（用 FIFO 做过实验确认 `fstat` 对「有内容的 FIFO」报 size=0，走同一路径；但 FIFO 的 open/close 延迟约 100 µs 会淹没基准，故不作为数字引用。）

### 实测数据（5000 进程 / 100 账号，本机 Intel i5-7360U / Go 1.25.5）

| 项 | 现在 | 优化后 | 差 |
|---|---|---|---|
| 4 个采集器各自聚合（cpu/io/mem/processes 各建 map + 各排序） | 1135 µs / 901 KB / 272 allocs | **263 µs / 238 KB / 118 allocs** | **4.3×** |

| 每进程路径拼接（`Itoa` + 3 次 `+`） | 1122 µs / 19901 allocs | **936 µs / 15000 allocs** | 少 4901 次分配 |

三处合计：**每次抓取约省 1.2 ms CPU + 约 1.1 MB 垃圾**（5000 进程的主机）。反直觉点：把所有字段放进**一次**聚合（9 个字段，比任何单个采集器都多）反而快 4.3× —— 说明成本在 map 遍历次数，不在字段数。

### 结构与语义层面的两项（**需要授权**，未动）

1. **把快照重建移出抓取路径**（后台刷新 + stale-while-revalidate）。关键论证：**TTL(2s) < scrape_interval(10s) ⇒ 每次抓取都在付完整重建**，TTL 只起"同一次抓取内去重"作用。所以挪到后台的新鲜度代价几乎为零，抓取路径上 15000 次 open/read/close 直接归零。代价：总 I/O 不变只是搬到后台；interval 越小总 I/O 越高。
2. **每进程 3 次 open → 2 次**：RSS 可无损改从 `/proc/<pid>/stat` 第 24 字段取；但 UID 只在 status 里，整份砍掉必须用 `/proc/<pid>` 目录 `st_uid`，而那是 **euid 不是 ruid** → setuid 进程归属会变。

### 本轮查证并写进技能库的硬结论

- `/proc/<pid>/stat` 第 24 字段 `rss` **单位是页**；`VmRSS_kB = rss_pages * (PAGE_SIZE/1024)`，与 status 的 VmRSS **数学等价**（同源 `get_mm_rss()`，status 侧走 `PAGES_TO_KB()`）。
- `/proc/<pid>/status` 的 `Uid:` **第 1 列是 ruid**（四列＝实/有效/保存/文件系统）；`/proc/<pid>` 目录的 `st_uid` 是 **euid** —— 内核 `task_dump_owner()` 默认 `cred->euid`，且目录的 mode 恰为 `S_IFDIR|S_IRUGO|S_IXUGO` 时**跳过** dumpable→root 改写。
- **技能库里"`stat("/proc/<pid>").st_uid` 就是真实 uid，可省掉读 status"是条错误建议，已改正并标注作废。**
- `/proc/<pid>/stat` 中带 `[PT]` 标记的字段（26–30、35、45–52）权限不足时**静默显示 0**；我们用的 12/14/15/20/23/24 都不带 `[PT]`。

## user_*.go 指标正确性审计（只读分析，未改任何代码）

用户要求「详细分析每个 go 文件，有没有哪些获取指标异常的情况」。逐文件读完 10 个实现文件 + 4 个测试文件，并对每个结论做了实证（读上游/procfs 源码、man page、写最小复现程序），**本轮零改动**。完整结论见当次回复，这里只记硬结论与被证伪的旧认知。

### 唯一会「全站失败」的一类：重复标签值 → HTTP 500

实测（/tmp/dupmetric，最小复现）：
```
collected metric "node_user_use_disk_total" { label:{name:"env" value:""} ... }
was collected before with the same name and label values
```
`promhttp` 的 `ErrorHandling` 默认是 `HTTPErrorOnError`（`= iota = 0`，见 client_golang v1.23.2 `promhttp/http.go:337`）→ **整个 /metrics 返回 500，所有采集器一起消失**，比 broken pipe 严重。
本仓库唯一命中点：`node_user_use_disk_total{username,pwd,env}`，标签来自 /etc/passwd，两行落进同一组标签值（共用家目录 / provisioning 追加重复行）即触发。

### 值错类

1. **`user_cpu.go` 两个指标的 `_seconds_total` 实际是 jiffies**。`utime/stime`（stat 14/15）与 `/proc/stat` 的 `cpu` 行都是 USER_HZ 滴答。上游为证：`procfs@v0.19.2/proc_stat.go:39 const userHZ = 100`、`stat.go:103 CPUStat.User /= userHZ`、`ProcStat.CPUTime()` 同样 `/userHZ`。**两个指标同源所以比值仍然正确**，但绝对值差 100 倍。
2. **`getSystemTotalTime` 把 `/proc/stat` 第 1 行所有字段直接求和 → guest 双计**。上游 `cpu_linux.go:402` 原话：`// Guest CPU is also accounted for in cpuStat.User and cpuStat.Nice`。跑虚拟机的宿主上系统总时间虚高 → 每用户占比被低估。
3. **`user_diskinfo.go` 家目录是符号链接时上报的是链接自身大小**。man7 du(1)/GNU coreutils 9.11：`-P, --no-dereference  don't follow any symbolic links (this is the default)`。`os.Stat` 却跟随 → `IsDir()` 为真 → 走 `du -sb -- path` → du 不跟随 → 报 strlen(target) 字节，且 > 0 不会被 `<= 0` 过滤。实测 BSD du：real=512 / link=0，`-H` 后 link=512。修法 `du -sbH` 或 `os.Lstat`+`EvalSymlinks`。

### 语义类（名字/help 与取值不符）

- `node_user_io_*` 四个指标 + 每用户 CPU 都是「**当前存活进程**的进程级累计值之和」→ **会下降**，但名字带 `_total` 被当 counter，`rate()`/`increase()` 遇下降按 counter reset 处理会**大幅高估**，`delta()` 给负尖峰。**没有任何 PromQL 函数能正确表达「每用户速率」**。
- `node_user_use_memory_total` = ΣVmRSS → **共享页重复计数**（每进程各算一遍），可能超过物理内存。
- 每用户 CPU 只取 utime+stime（不含 cutime/cstime）→ **短命子进程的 CPU 完全不计入**，脚本/cron/构建类用户系统性偏低。
- `du -sb` 是 apparent size 不是占用：稀疏文件按表观计、已被删除但仍有进程持有的文件看不见 → Σ每用户 ≠ df。
- `user_shm` 只按**属主**归集，被 attach 的进程所属用户计 0，`nattch` 未使用。
- `user_processes.count` 含内核线程（kthread 也有 `Uid: 0`）→ root 的 count 虚高 100+。

### 序列静默消失 / 静默为 0

- `user_diskinfo`：`stat.size <= 0` 直接跳过 → **空家目录（合法 0）与 du 失败表现为同一个现象**「序列不存在」，无法区分；删掉的家目录（返回 `0,nil`）同样只表现为消失。
- `user_diskinfo`：首轮 pass 未完成时 `cache == nil` → **一条指标都不发**（连 `cache_age_seconds` 都没有），且 `node_scrape_collector_success{collector="userdiskinfo"}=1` 看起来健康。
- `user_corefile`：`parseCorePrefix` 对 `lastSlash <= 0` 返回 ""，于是 **core_pattern 的目录是 `/`（如 `/core.%e.%p`）时完全不上报**，success=1，无任何日志。另一面：`core_pattern` 指向某目录里的固定文件名（`/data/core`、`/tmp/core.%p`）时，**该目录里所有普通文件都会被当成 core 文件上报**，再被 1000 上限截断。
- `user_cpu`：`getSystemTotalTime` 失败 → 整个采集器 0 条，连不依赖它的每用户指标一起消失。
- `user_processes`：stat 不可读时进程仍 `procs++` 但 threads 计 0 → `threads_count` 瞬时 < `count`。
- `user_io`：非 root 时 `/proc/<pid>/io` 对他人进程 EACCES → 只剩 exporter 自己能读的进程，指标**静默接近 0**。

### 标签陈旧 / 错人

`user_utils.go` 的 `refreshUIDNameMap` **只在缺失时写入**（`if !exists`），所以 `passwdCacheTTL=5min` 对已存在的 UID 完全失效 → 改用户名、或 UID 被复用后 `username` 标签**一直指向旧名字直到进程重启**。而 `user_diskinfo` 走 `parsePasswdFile`（整块替换，5min 生效）→ **同一时间同一个用户会出现两条不同 username 的序列**（disk 用新名、cpu/mem/processes 用旧名）。

### 其他

- `user_diskinfo.go` 的 `userdiskUseSudo()` 探针用 `context.Background()`（**无超时**），包在 `sync.Once` 里 → 若 `sudo -n` 卡住则 `wg.Wait()` 永久阻塞、后台刷新器彻底停止、`cache` 永远 nil → **磁盘指标永久缺失且无日志**。同文件其他调用都挂了超时，只有探针没挂。
- build tag：`user_meminfo.go` 写 `!nomeminfo`，与上游 `meminfo_linux.go:14` **完全相同** → `-tags nomeminfo` 一次禁掉两个采集器，且无法单独排除 usermeminfo。惯例应为 `!no<注册名>`。（`!nocoreinfo`/`!nodiskinfo` 各自唯一，无叠加，但同样不符合惯例。）
- `user_io.go` 里 `agg.username == ""` 的跳过分支是**死代码**（`lookupUsernameID` 最差返回数字 UID 字符串，不会返回空串）—— 与上一轮的结论一致。

## user_*.go 审计问题的修复（用户「修复这些问题」= 授权 A+B 两桶，已完成）

### S0 重复标签值（最高优先级）
- `user_diskinfo.go` `parseUserDiskLabels` 按 `{username,pwd,env}` 三元组**去重**。`/etc/passwd` 出现两行同名账号时，`prometheus.Gather` 会拒绝整个 registry → **整个 `/metrics` 返回 500**（不是一个采集器的事）。`env` 由 username 推导，无法区分同名两行。
- `measureUserdiskSizes` 的 `paths` 一并去重（两个账号指向同一家目录时不再跑两遍 du）。

### S1 值与单位
- `user_cpu.go` 新增 `userCPUHZ = 100`，`process_cpu_seconds_total` 与 `system_cpu_seconds_total` 都除以它。原值实际是 jiffies，比指标名声称的 seconds 大 100 倍（两者比值不受影响，所以一直没暴露）。
- `user_proc_parse.go`：`parseCPUSummaryTotal` 只累加**前 8 个字段**（新增 `cpuSummaryFields = 8`）。`guest` 已含在 `user` 内、`guest_nice` 已含在 `nice` 内，全加等于重复计数。停在第 8 个也让 <2.6.24（无 steal）/<2.6.33（无 guest）的内核仍可解析。
- `user_diskinfo.go`：`du -sb` → **`du -sbH`**。`-H`(`--dereference-args`) 只跟随命令行给出的符号链接，家目录本身是链接时才报对；GNU du 默认 `-P` 会报链接自身大小。

### S2 序列消失 / 失败扩散
- `user_diskinfo.go` `Update` 去掉 `stat.size <= 0` 过滤。`userdiskDirectorySize` 对不存在的家目录**故意返回 0**，再过滤一次就把「目录已删除」变成序列静默消失。
- `user_cpu.go`：`getSystemTotalTime` 失败改为**降级**（warn + `systemTotalTime=0`），`GetStats` 不再因此返回 error。原来 `/proc/stat` 一个文件读不到会拖垮全部 per-user 序列。
- `user_corefile.go`：新增文件名模式过滤，避免把目录里的 README 等非 core 文件误报成 core dump；`/` 与空目录分别显式处理（`/` 拒绝扫描并 warn，不再静默）。

### S3 标签错人
- `user_utils.go` `refreshUIDNameMap` 改为**每次 refresh 覆盖** `/etc/passwd` 覆盖到的 UID。原来的 `if !exists` 让错名字永久保留，且与 `user_diskinfo` 的 `parsePasswdFile`（整块替换）不一致 → 同一用户出两条 username 不同的序列。

### 死锁 / 计数一致性 / build tag
- `user_diskinfo.go` 新增 `userdiskSudoProbeTimeout = 10s`，`userdiskUseSudo` 探针不再用 `context.Background()`。原来 `sudo -n` 卡住会让 `sync.Once` 永久阻塞后台刷新器。
- `user_proc_aggregate.go`：stat 读不到时 threads 记 **1**（`num_threads >= 1` 恒成立），消除 `threads_count < count` 的不可能状态。
- 7 个 build tag 全部改为 `!no<注册名>`：`!nousercpuinfo / !nouserio / !nousermeminfo / !nouserprocesses / !nouserdiskinfo / !nousercoreinfo / !nousershm`。⚠️ **行为变化**：`-tags nomeminfo` 以前会连带禁掉 `usermeminfo`，现在不会。已验证 7 个 tag 各自 `go build -tags` 可独立禁用。

### 新增文件
- `collector/user_corefile_pattern.go`（无 build tag，纯字符串逻辑，macOS 可单测；沿用 `user_diskinfo_stale.go` / `user_shm_parse.go` 的既有约定）
- `collector/user_corefile_pattern_test.go`

### 有意不修（属设计选择/内核限制，非 bug）
- `node_user_*_total` 非单调（进程退出后下降）→ `rate()` 不可用。改类型/改名破坏指标契约，用户明确禁止。
- 非 root 时 `/proc/<pid>/io` 对他人进程 EACCES → `user_io` 只能看到自己拥有的进程。内核 `PTRACE_MODE_READ` 限制，只能 root 运行。
